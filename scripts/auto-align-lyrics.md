# auto-align-lyrics.py 技术说明

给一个 YouTube 链接 + 一份歌词文本，自动生成一份能直接贴进 `songs/*.js` 的
时间轴草稿，不用再自己在网页里逐句按空格标。

## 整体流程

```
YouTube 链接
   │  yt-dlp
   ▼
音频文件（.wav）
   │  Demucs（人声分离）
   ▼
人声轨（去掉伴奏）
   │
   ├──────────────┐
   ▼              ▼
Whisper 识别    aeneas 强制对齐
   │              │
   ▼              ▼
逐字比对得出     DTW 声学对齐
每句时间          得出每句时间
   │              │
   └──── 融合 ────┘
          │
          ▼
   TIMES 时间轴草稿
```

## 每一步在做什么、为什么需要它

### 1. yt-dlp 下载音频

YouTube 最近对网页/iOS 客户端上了 SABR 限流，直接下载会报 "page needs to be
reloaded" 的错。改用 `--extractor-args youtube:player_client=android` 换一个
不受限的客户端拿流，画质会降到比较低的档位（如 itag 18），但只是要给 Whisper
和 aeneas 听，够用。

### 2. Demucs 分离人声

**这一步影响非常大。** 实测直接把原始混音（人声 + 伴奏）喂给 Whisper，
识别命中率只有二成多；换成 Demucs（`htdemucs` 模型）分离出的纯人声轨，
命中率能到七八成。语音识别模型是照着「干净人声」训练的，伴奏一响就容易懵，
这个差距比预期的大得多。

### 3a. Whisper 识别 + 逐字比对（`align()`）

Whisper 把人声轨转成文字，带每个词的时间戳。但我们已经有「正确」的歌词了，
不需要它猜对是哪几个字——只需要拿它输出的文字，去跟已知歌词做**逐字比对**
（`difflib.SequenceMatcher` 找最长公共子串），把匹配上的位置换算回时间。

这条路精度很高（在已验证的测试歌里，命中的句子中位数误差只有 0.6 秒左右），
但有一个**结构性的坑**：如果歌词里有大段逐字重复的内容（副歌唱三遍这种），
比对算法的目标是让「匹配上的总字符数最多」，它并不知道「这是第几次重复」。
如果 Whisper 对某一次重复的转录质量恰好比另一次差一点，算法可能会为了凑
更长的匹配，把两次重复的歌词文字都对到那次转录更干净的地方，导致中间那次
重复完全被跳过、后面的内容因为可用文本被提前用掉而对到歌曲结尾之外——
错误可以达到几十秒。这不是文字识别不够准的问题，而是「已知文本有重复」这
件事本身，对纯文本比对来说有歧义。

（调试过程中还试过「一句一句顺序比对、只往前走不回头」的几种写法，理论上
应该能避开这个歧义，但实测反而更差——要么短文本在没约束的搜索范围里瞎凑
巧合，要么用歌词本身的字数去估计「这句唱了多久」，因为 Whisper 经常漏掉
虚词，每句都稍微估多一点，一路滚雪球越错越远。最后放弃了这个方向。）

### 3b. aeneas 强制对齐

`aeneas` 是专门做「已知文本、找时间戳」的工具，原理跟 Whisper 完全不同：

1. 用 `espeak` 把已知歌词**合成**一份机器泰语语音（不是识别，是朗读）
2. 把合成语音的声学特征（MFCC）跟真实人声轨做 DTW（动态时间规整）对齐
3. 因为全程没有「猜文字」这一步，天然不会被「歌词重复」搞混——合成语音本身
   就是严格按歌词顺序排列的，DTW 对齐是把整条音频时间轴按顺序分给这些片段，
   结构上不可能把后面的片段错误地对回前面。

代价是精度不如 Whisper：跟着**机器合成语音**的匀速节奏对齐，跟真人唱歌
（拖长音、转音、抢拍）的实际节奏有出入。实测中位数误差在 1~1.2 秒左右，
比 Whisper 命中时的 0.6 秒要粗，但**不会出现离谱的错误**——最差情况也就
十几秒，不会像 Whisper 那样偶尔错出几十秒。

aeneas 官方内置的语言表是十年前的老版本，没有收录泰语；用的又是经典 espeak
的库名 `libespeak`，而 Homebrew 现在装的是它的继任者 `espeak-ng`。脚本里
用两个小办法绕过去：

- 运行时给 `ESPEAKTTSWrapper.LANGUAGE_TO_VOICE_CODE` 打个补丁，把 `tha`
  映射到 espeak-ng 的泰语语音代码 `th`
- 装依赖那一步把 `libespeak-ng.dylib` 软链成 `libespeak.dylib`，让编译
  aeneas 的 C 扩展（`cew`）时链接器能找到（只在**安装**这一步需要，运行时
  不需要这个软链也能跑）

如果目标环境里没有装 espeak / aeneas 装不上，脚本会自动跳过这一路，退回
纯 Whisper 方案（准头和稳定性都会差一截，但至少能跑）。

### 4. 两路结果融合

对每一句：Whisper 给出的时间「有信心」（真的落在识别文本的匹配块里）**且**
跟 aeneas 给出的时间差距在合理范围内（默认 5 秒，`--sanity-threshold` 可调）
——两边独立算出来的结果互相印证，才采信 Whisper 的高精度结果；否则用 aeneas
兜底。逻辑是：

- aeneas 从原理上不会错得离谱，但也不特别准
- Whisper 通常很准，但偶尔会因为「歌词重复的歧义」错得很离谱
- 两边一起兜底，比单独用哪一个都稳——精度接近 Whisper，稳定性接近 aeneas

第一句是例外：aeneas 的第一个片段永远从 0 秒起算（它不知道前奏有多长，这个
数字没有参考价值），所以第一句不跟 aeneas 比较，直接采用 Whisper 自己的
估计，就算标了「不确定」也比硬编码成 0 更接近真实值。

输出里没对上/没被采信的句子会标一个 `❓`，提示回头人工核一遍。

## 实测效果

在 `safe-near-me`（已经手工逐句核对过全部 47 句、可以当标准答案用）上反复
验证：

| 方案 | 平均误差 | 中位数误差 | 最差情况 |
|---|---|---|---|
| 只用 Whisper（文字比对） | 9.3 秒 | 0.63 秒 | 42 秒 |
| 只用 aeneas（强制对齐） | 2.4 秒 | 1.2 秒 | 16 秒 |
| 两路融合 | 1.5~1.9 秒 | 0.3~0.6 秒 | 11 秒 |

## 已知局限

- **英文桥段**：整句是英文的行，aeneas 用泰语音色合成对不上，精度明显变差
- **副歌反复段落**：就算融合方案兜住了不会错得离谱，精度也比其它段落差
  一截，比不上手动逐句标
- 这些行脚本会标 `❓`，但没标 `❓` 不代表百分之百准，只是相对更可信

## 依赖

```bash
pip install yt-dlp faster-whisper demucs soundfile aeneas
brew install espeak-ng   # macOS
```

用法和歌词文件格式见脚本文件顶部的 docstring（`python3
scripts/auto-align-lyrics.py --help`）。
